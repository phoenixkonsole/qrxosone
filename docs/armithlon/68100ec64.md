# 68100EC64 instruction set

Version 1, draft. The 68100 with 64-bit registers, addresses and operations, for a 64-bit AROS with
SMP. EC as on the 68EC040: no MMU. Reference code: `upstream/armithlon/2.6/engine/full68k/qrx68100ec64.c`,
tests in `tests/ec64_tests.c` and `tests/ec64_diff_tests.c`.

The existing 68100 and its JIT are unchanged. This core is separate and is not reachable from a guest
yet.

## Modes

| Mode | Registers and addresses | Prefix |
| --- | --- | --- |
| 32-bit (reset) | The 68040's integer instructions | Faults |
| Long | 64 bits | Allowed |

`MOVEC Rn,$80F` sets long mode from bit 0. `MOVEC $80F,Rn` reads it, and `MOVEC $80E,Rn` reads the core
number. See below for supervisor state, exceptions and several cores.

## Registers

D0 to D15 and A0 to A15, 64 bits each, in long mode. A7 is the stack pointer. PC is 64 bits.

## Prefix

Line A was free on the 68k, so the prefix word is `$A0xx`, directly before an ordinary instruction.

| Bit | Name | Meaning |
| --- | --- | --- |
| 4 | N | `MOVE` leaves the flags alone. Other instructions fault with it |
| 3 | W | `.L` becomes `.Q`, 64 bits |
| 2 | R | Adds 8 to the register in bits 11 to 9 (the destination field of `MOVE`) |
| 1 | X | Adds 8 to the index register |
| 0 | B | Adds 8 to the register in bits 2 to 0 |

`$A020` to `$AFFF` are reserved and fault. N exists because a compiler may place a register copy between
a compare and its branch. A stock assembler can write the prefix as a `.word`, see
`guest/ec64/fnv64.S`.

## Long mode rules

- **Operand sizes:** `.B` and `.W` writes to a data register keep the upper bits. `.L` writes clear bits
  63 to 32. `.Q` writes all of it. Clearing avoids a dependency on the old value, which suits the JIT.
- **Flags:** Computed at the operand size.
- **Address registers:** Always 64 bits. `MOVEA.W`, `MOVEA.L`, `ADDA` and `SUBA` sign extend the source.
  Under W they take all 64 bits.
- **`MOVEQ`:** Sign extends to 64 bits.
- **Immediates:** `#imm` under W has 8 bytes.
- **Addressing:** `(xxx).W` and `(xxx).L` sign extend. In `d8(An,Xn.L)` the index is the whole register.
  The 68020 full format works without its memory indirect forms.
- **PC relative destinations:** `(d,PC)` and `(d,PC,Xn)` may be written to in long mode, for all instructions
  with an alterable operand, so that a program can reach its data within 2 GB without a register.
- **Stack:** `JSR`, `BSR`, `RTS`, `PEA`, `LINK` and `UNLK` use 8 bytes.
- **`MOVEM`:** `.L` stores the low half and sign extends on load. Under W it stores all 64 bits.
- **Wide forms under W:** `EXT` from 32 to 64 bits, `SWAP` swaps the halves, `MULU` and `MULS` are 64 x 64 with
  an optional high half, `DIVU` and `DIVS` are 64 / 64. Bit numbers on a data register run to 63, as do
  shift counts.
- **Atomics:** `TAS` and `CAS` up to `.Q` are atomic on aligned addresses, also between host threads. Other
  aligned accesses keep the 68040's bus order.

## Supervisor state and exceptions

In long mode, once VBR has been written, every fault, trap and interrupt goes through the vector table.
Until then a core stops and reports, which the instruction tests rely on.

- **States:** Supervisor and user, with two stack pointers. A core starts in supervisor state.
  `MOVE USP`, `MOVEC $800`, `RTE`, `STOP`, `RESET`, `MOVE to SR`, `ANDI`, `ORI` and `EORI to SR`,
  `MOVE from SR` and every `MOVEC` are privileged.
- **Vector table:** 256 entries of 8 bytes at VBR (`MOVEC $801`), 8-byte aligned. The vector numbers are the
  68000's: 2 bus fault, 4 illegal, 5 divide by zero, 6 CHK, 7 TRAPV and TRAPcc, 8 privilege, 10 line A (a
  reserved prefix), 11 line F, 24 + n interrupt level n, 32 + n `TRAP #n`.
- **Frame:** SR (2 bytes), format and vector offset (2), reserved (4), PC (8). Format 1 adds the fault address
  (8). `RTE` reads the format.
- **Which PC:** Faults, illegal and privilege give the instruction's own address, traps the next one. A bus
  fault does not undo the instruction's address register updates: there is no MMU and so no restart.
- **Interrupts:** Seven levels as on the 68000, level 7 cannot be masked. On this machine level 5 is the
  core's timer and level 6 a signal from another core.
- **No exception frame possible:** The core stops with a double fault when the stack or the vector entry is
  outside RAM.

### Control registers

| `MOVEC` | Name | |
| --- | --- | --- |
| `$800` | USP | The user stack pointer |
| `$801` | VBR | Writing it switches exceptions on, in long mode |
| `$80A` | Start stack | Stack for the next core this one starts |
| `$80B` | Cores | Number of cores, read only |
| `$80C` | Timer | Period of this core's timer interrupt in microseconds, 0 is off |
| `$80D` | Signal | Write a mask of cores: each gets a level 6 interrupt |
| `$80E` | Core | This core's number, read only |
| `$80F` | Long mode | Bit 0 |
| `$8F0`, `$8F1` | Console, end | Test machine only: writing `$8F0` puts a character out, reading it takes the next input character or -1; writing `$8F1` ends the run with a value |

### Several cores

Core 0 starts at reset. The others wait. The first signal a waiting core gets starts it: it takes the VBR of
the core that sent the signal, the stack that core named in `$80A`, and long mode, and takes the level 6
interrupt at once. Its frame holds no PC to return to.

Memory between cores follows the 68040's bus order, and `TAS` and `CAS` are atomic.
`qrx68100ec64_machine.c` runs each core on its own host thread.

## Host floating point ($AFnn)

The core has no FPU; the m68k64 compiler calls compiler-rt's soft float (`__addsf3`, `__mulsf3`
and the others) for every float operation, 50 to 200 instructions each. In long mode the one-word
instruction `$AF00 | n` (a line-A code the prefix `$A000-$A01F` leaves free) does such an operation
on the host: D0 and D1 hold the operands as raw IEEE bits (single precision in the low 32 bits), D0
gets the result, nothing else changes. The results are those of compiler-rt bit for bit, NaNs and
the conversions to integers included (`include/qrx_ec64_hostfp.h` lists the operations). The JIT
calls the same C code as the interpreter, so a block goes on after it. An `n` without an operation
is an illegal instruction, as is the instruction outside long mode.

The guest side is `tools/armithlon/aros-qrx/qrxhostfp`: `make-hostfp.py` writes the replacements
(`hostfp.S`, and `hostfp.inc` for C), each one loading its arguments into D0 and D1, `$AFnn` and
`RTS`. ThunderCat links them into libxul. `fptest.c` compares them with compiler-rt in the guest:
7354 results, the same with the JIT on and off.

Measured with `qrx_ec64_run --profile` (ThunderCat loading qrx.rocks): soft float took about 30% of
all the time, most of it in WebRender's software rasteriser (SWGL).

Measured end to end (x86-64 host, 2 cores, JIT, same kernel and fixes, ThunderCat with compiler-rt's
soft float against the same build with `$AFnn`; a screenshot every 20 s, read by
`tools/armithlon/ec64bench.py`, so each time is up to 20 s late):

| | soft float | host floating point |
| --- | --- | --- |
| start page: window / content | 140 s / 700 s | 160 s / 420 s |
| qrx.rocks: window / page drawn | 140 s / 740 s | 140 s / 420 s |
| from the window to the page (qrx.rocks) | 600 s | 280 s, 2.1 times faster |
| instructions in 900 s (start page) | 130.5 billion | 56.0 billion |

## ARMithlon board

In the emulator (`qrx_ec64_run`, see below) the machine has devices in a device window: the top
4 GB of the address space, from `$FFFFFFFF00000000`, in long mode only. There is no MMU, so programs
in user state reach them too. Registers are big endian; an access of another size or to an unknown
register is a bus fault. The offsets (`include/qrx_ec64_board.h`):

### Global Forbid

AROS keeps `Forbid()` and `Disable()` per core. With tasks on several cores (`$3C0`), Amiga code that
guards shared lists with `Forbid()` would race. With `QRX_EC64_GFORBID=1`, or with
`QRX_EC64_SMP_SPREAD=1`, or once the kernel has written 2 to `$3C0`, unless `QRX_EC64_GFORBID=0`,
`qrx68100ec64_machine.c` makes them global:
in the JIT's dispatcher a core reads its TLS (`A8`): `IDNestCnt` at +28, `TDNestCnt` at +29, the
number of kernel spinlocks it holds at +31, and the parts of both levels that exec takes around data it
guards with spinlocks as well (+44 `LocalTDNest`, +45 `LocalIDNest`: semaphores, ports, memory,
signals; `rom/exec/exec_local.h`). A core in user state with either level, less its local part, at 0
or above owns the machine; it goes on once every other core is asleep (`STOP`), in supervisor state,
or standing in the dispatcher. The others stand still until it lets go, except while they hold a
spinlock or have an interrupt to take. Every wait has a limit (5 ms for the owner, 50 ms for the
others), so a program that waits in `Forbid()` for another core is slowed down, not hung.

Blocks chain as usual: after every change of the two levels the kernel runs the gate point `$AFF0`
(a no-op, but no block holds it, so the dispatcher and its gate come first), and a chain runs at most
4096 instructions before the dispatcher looks again; a core that takes the global Forbid sets the
others' `gate_kick`, which makes their next indirect jump go to the dispatcher. The JIT has to be on
(`QRX_EC64_JIT=0` leaves the cores per-core).

Measured (ThunderCat on qrx.rocks, x86-64, 2 cores): exec's own sections made 88% of 7.2 million
global Forbids in 400 s; with them left out, 1.2 to 1.4 million remained.

Tasks on both cores are the default once the kernel says it can: at boot it writes 2 to `$3C0`
(the task state lock in the scheduler, exec's local levels, the gate points and the CAS atomics are
in it). The machine then reads `$3C0` as 1 and turns the global Forbid on. Older kernels never write
it and keep their tasks on one core. `QRX_EC64_SMP_SPREAD=0` keeps one core, `=1` forces both.

Measured (ThunderCat on qrx.rocks, 700 s, x86-64 host, two runs side by side, a screenshot every
20 s):

| | one core (`QRX_EC64_SMP_SPREAD=0`) | both cores (default) |
| --- | --- | --- |
| instructions a second | 155.6 million | 196.2 million (110.7 + 85.4) |
| qrx.rocks drawn after | 320 s | 340 s (one step of the screenshots) |
| global Forbid | - | 0.9 million times; 0.4 to 0.5% of a core standing still |
| faults | none | none |

What it took, in the order it was found:
- **Task state lock.** `Wait()` marks its task waiting while it still runs; a `Signal()` from the
  other core took it off a list it was not on yet and made it ready, and two cores ran it on one
  stack (double fault, "core_Switch: called on invalid task"). `m68k64_TaskStateLock` now covers a
  task's way between the scheduler's lists, and a task still on a core only changes state.
- **Local levels.** exec's sections around data it guards with spinlocks (semaphores, ports,
  memory, signals, `WaitIO`) no longer take the global Forbid: 7.2 million times in 400 s before.
- **Gate points.** Blocks chain again with the global Forbid on (before: 55 million instructions a
  second on both cores together).
- **Spinning in the gate** instead of `nanosleep()`: standing still went from 8-11% to 1-1.5%.
- **CAS atomics.** `aros/atomic.h` did not know m68k64 and used its `Disable()` fallback, so every
  `Signal()` and `Wait()` took the global Forbid: 3.6 million down to 0.9 million times.

Endurance runs on both cores: 300 rounds of shell commands with background tasks; ThunderCat from
the start page through typing an address, qrx.rocks and the About window, 1350 s; no faults.
What is left of the global Forbid is mostly timer.device's own `Disable()`.

The console stays MOVEC `$8F0` (out and in) and `$8F1` ends the run, as on the test machine. In the
window, typed text goes to the console input.

### OpenGL 3.3

Service 13 (`full68k/qrx_gl3.c`) runs a command stream of the guest library
[tools/qrxgl68k/guest/qgl3.c](../../tools/qrxgl68k/guest/qgl3.c) on an OpenGL 3.3 core context of the
host: EGL surfaceless on Linux, CGL core on the Mac. It is what WebRender draws with. The request block
is service 8's with the context in word 7. One GL thread of the engine owns every context (EGL lets a
context be current on one thread only, and the cores are host threads); a call hands the block over and
waits.

[gen3.py](../../tools/qrxgl68k/gen3.py) makes the stubs from the host's `glcorearb.h`: 329 of the 345
functions of OpenGL 1.0 to 3.3 core. Not carried: mapped buffers, client-side pointers
(`glGetPointerv`, `glGetVertexAttribPointerv`, `glMultiDrawElements`), the `char **` calls and the
packed `glVertexAttribP*`. What the host does with pointers:

| Data | How |
|---|---|
| Values, inline arrays (`glUniform*v`, `glDelete*`, `glGen*`, `glGet*`) | swapped by element size as they are read or written |
| Buffer data (`glBufferData`, `glBufferSubData`) | passed through as bytes: vertex, instance and index data must be little endian |
| Attribute and index pointers | offsets into the bound buffers |
| Texels | the guest's own; the host keeps the swap-bytes pixel store on, which is right for every type, from guest memory and from pixel buffers |
| Framebuffer 0 | a host framebuffer object of the size the guest asks for; read back as A R G B or B G R A bytes, top row first |
| Extensions | only those whose calls the door carries (a program that saw `GL_ARB_texture_storage` would call `glTexStorage2D`) |

`tests/gl3_tests.c` draws on the host with a GLSL 330 program, a vertex array object with per-instance
data, a texture from big-endian texels, an FBO blit and a fence, and checks the pixels; here on Mesa's
llvmpipe (a software GPU: the build container has no other). `tools/qrxgl68k/ec64/EC64GL3Test` does
the same from QRX OS One 64 and passes there (2026-11-27, two cores, the same llvmpipe): it sees
GL 4.5 core, GLSL 4.50 and 46 of the host's 229 extensions, and the frame it reads back is the two
instanced quads in the texture's colour times the tint on the cleared blue.

In Gecko (`gfx/gl/GLContextProviderAROS.cpp`) WebRender gets a context per window; `SwapBuffers`
reads the frame back into the widget's buffer and puts it into the Intuition window as SWGL's frames
are. WebRender on big endian puts vertex and index data into little endian per vertex descriptor, and
uploads without pixel buffers. Without the door GfxInfo blocks hardware WebRender and SWGL draws as
before.

Measured (2026-11-27, x86-64 container with 4 cores, no GPU: the host's OpenGL is Mesa's llvmpipe,
which renders on the same CPU cores the emulator runs on; QRX OS One 64 on two cores with the JIT,
screen 800 x 600, ThunderCat loading the qrx.rocks copy; a screenshot every 20 s, read by
`tools/armithlon/ec64bench.py`, so each time is up to 20 s late):

| | SWGL (`QRX_EC64_GL3=0`) | WebRender on the GL 3.3 door |
| --- | --- | --- |
| window | 80 s | 80 s |
| page drawn and settled | 220 s | 200 s |
| GL door | none | 68412 streams, 729749 calls in 600 s |

The page looks the same both ways. At this size the time to the first page goes mostly to starting
the browser and to layout and JavaScript, not to drawing, so the difference is within one picture's
interval; it also has llvmpipe competing with the emulator for the four cores. A host with a real GPU,
larger windows and scrolling are what this path is for and are still to be measured.

## Not there yet

- Memory indirect addressing, `MOVE16`, trace, the FPU. `CAS2` is not atomic.
- Bit fields work on at most 32 bits, also in long mode.
- A JIT. The interpreter ran 41 to 77 million instructions per second in the tests, far too slow for a browser.
- The emulator runs the core as its own program next to the 32-bit QRX OS One, with no JIT yet.
- Calling 32-bit libraries from long mode or the reverse. A 32-bit AROS program does not run on a 64-bit
  AROS without this.
- The assembler (`llvm-mc`) does not know the privileged instructions yet; they go in as `.short`. A 64-bit AROS boots on the core up to its shell, see [tools/armithlon/aros-qrx](../../tools/armithlon/aros-qrx/README.md).
