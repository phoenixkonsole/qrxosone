# QRX86 22.5.12 → ARMITHLON Metal Bridge (code, not only a plan)

**Existing source reviewed:** `x86-runtime-22.5.12/win32/dx.c` (DirectDraw,
DirectSound, DirectInput3), `gdi.c`, `backend_headless.c`, `backend_aros.c`,
`qrxwin.h`, `qrx_win32_main.c`, `tests/run-host-tests.sh` in the audited
`phoenixkonsole/qrxosone` branch.

**Integration point:** The existing `qbackend` vtable includes `present()`.
The patch tool identifies the exact existing `hl_present()` definition.
When compiled with `QRX86_HOST_GPU` it invokes
`qrx86_gpu_backend_present(t->surf.pix, t->surf.w, t->surf.h)`, where pixels
are the already HLE-rendered host 32-bit 0x00RRGGBB values. This avoids
mistaking an x86 guest address for a native host pointer. The bridge either
emits an in-process GPU frame or serializes the Win32 framebuffer through a
small versioned Unix socket protocol (Q86F); Metal renders it as a texture.

**This is deliberately backend-level, not fake d3d9.dll or glide2x.dll.**
All original DirectDraw/Win32 bitmap format semantics remain implemented
within the existing QRX86 core. Future D3D/GL command translation must happen
at the guest API import/HLE layer before rendering, preserving contexts,
object lifetime, shader formats, handles, synchronization and error semantics.

The `backend_aros.c` remains unchanged. On AROS m68k it still uses CyberGraphX
and its native RTG hardware abstractions. That backend cannot directly call
host POSIX functions. It will benefit from ARMITHLON's GPU only after the
real AROS qrxvirt graphics.hidd driver is completed. The host patch is guarded
with `!defined(__AROS__)` to prevent accidental ABI mixing.

The host build wrapper is experimental; the existing QRX86 host-tests use GCC
and a Linux-x86_64 toolchain. macOS ARM64 compiler validity and runtime
performance must be checked on the actual machine.
